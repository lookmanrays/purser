# P2-06 Test coverage edges

## Goal

`covered_by` edges from symbols to the tests that execute them, so observers can run exactly the regression tests a change can affect.

## Context

The design's observer for regression tests (P4-03a) selects tests from these edges.

## Design

- Go: list tests with `go test -list`, run each test function alone with `-run '^Name$' -coverpkg=./... -coverprofile`, parse profiles with `golang.org/x/tools/cover`, and map covered blocks to the symbols whose ranges contain them.
- TypeScript (vitest): run each test file alone with Istanbul JSON coverage and map covered statements to symbols. Granularity is the test file.
- Test nodes: `test:go:<package>.<TestName>` and `test:ts:<repo-relative file>`.
- Results are cached by the SHA-256 of the test file and of the package's source files; unchanged tests are not rerun.
- Parallelism is limited by a setting; each run has a timeout. A failing test still contributes the coverage it reached and is marked `failed`.

## Out of scope

Coverage for languages other than Go and TypeScript, and line-level reporting.

## Test plan

Fixture Go module with three tests over overlapping functions; fixture vitest project with two test files; a cached rerun; a test that fails halfway.

## Acceptance criteria

- AC-1 The Go fixture produces exactly the `covered_by` edges in its golden file.
- AC-2 The vitest fixture produces exactly the `covered_by` edges in its golden file.
- AC-3 A second run with no changes executes no tests and produces the same edges.
- AC-4 Changing one source file reruns only the tests whose cache keys include it.
- AC-5 A failing test contributes its partial coverage and is marked failed.

## Definition of done

Standard Definition of done.

## Escalate if

Per-test Go runs are too slow on a benchmark repository; propose package-level granularity with numbers.
