# P0-03 specification contradictions

## Proposal envelope and operation validation

P0-03 requires every object schema to be closed and AC-4 requires rejection of an unknown field at any depth. The source of the v1 wire format, [`kernel-v1.md`](../../reference/python/docs/contracts/kernel-v1.md#canonical-bytes-and-hashes), gives proposal envelopes and their operations different validation boundaries. A malformed operation in an otherwise valid envelope receives a durable rejected receipt.

To verify the difference, I loaded `proposals[0]` and `binding` from [`wire-v1.json`](../../testdata/vectors/purser-v1/wire-v1.json) and added `unexpected: true` to `ops[0]`. Using `python3.11 -I` with `reference/python` on `sys.path`, the reference [`envelope`](../../reference/python/purser/kernel/gate.py#L68) accepted the proposal. Admission against a fresh temporary store returned `proposal_id: p-create`, `disposition: rejected`, `code: invalid_op`, and `revision: 1`. The same receipt appeared in the store snapshot. Rejecting this proposal at the envelope boundary would prevent that receipt.

Specify that `proposal` validates the v1 ingress envelope, with raw JSON operation entries preserved until operation validation. Apply AC-4 to schema-defined objects, including operation objects at their validation boundary. If P0-03 must expose strict operation schemas, give them a separate schema name and say which callers use them. This lets the frozen tests assert both the closed envelope and the operation rejection that preserves v1 receipt behavior.

## Snapshot names and fixture shape

The reference [snapshot contract](../../reference/python/docs/contracts/kernel-v1.md#ownership-and-compatibility) and `expected.snapshot_at_4` and `expected.snapshot_at_8` in the wire vector define the three keys `revision`, `head_hash`, and `projection`. The [P0-06 golden-log format](P0-06.md#design) adds `projection_checksum` to each dumped snapshot row. All 515 committed golden snapshot rows contain that fourth key. AC-2 directs tests to the records in the golden rows. The brief's broader requirement to derive v1 field sets from both sources leaves it unclear whether the extra key is accepted on a `snapshot`.

Specify that `snapshot` is the three-key wire shape and `projection_checksum` belongs to the golden dump row. AC-2 can validate the records under `projection.records` in either source. If validating golden rows as full objects is intended, give the dump row its own schema.

## Go declarations and JSON pointers

The [record draft](../../contracts/records/records.draft.yaml) describes record fields and has no Go declarations. The brief gives the `Validate` function signature and requires Go envelope structs and a typed error. It leaves the names and fields of those types open, including the public way to obtain the JSON pointer. Under the [test-author playbook](../agents/test-author.md#3-write), stubs must use the contract's exact declarations. Freezing an AC-6 test would choose an interface for the builder.

Publish the exact Go declarations for `Validate`, the error and its pointer accessor, and the envelope types. Define the expected pointer for a missing property and an extra property, including whether it names the property or its containing object. Give AC-6 a case with one violation so it does not depend on ordering across unrelated errors.
