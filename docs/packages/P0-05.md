# P0-05 Tool and CLI schemas

## Goal

Schemas for tool contracts and for every CLI reply, so agents and scripts can rely on Purser's machine output.

## Context

The design's Tools section defines tool contracts. purser-main's `kernel-v1.md` (CLI surface) fixes the CLI reply shapes and exit codes.

## Design

- `tool-contract-v1.schema.json` with keys `tool`, `inputs`, `outputs`, `effects`, `deterministic` and `cost`. Keys match the design's tool example.
- `contracts/cli/` holds one schema per reply: `init`, `propose`, `status`, `why`, `replay`, `frontier`, `context`, `error`. Shapes follow `kernel-v1.md`.
- `contracts/cli/exit-codes.yaml`: 0 success, 2 invalid input, 3 pending, 4 rejected or not found, 5 unauthenticated, 6 storage unavailable, 7 integrity or unsupported version.
- Later CLI commands (graph, plan, run, cost) add their schemas in their own packages.

## Out of scope

No CLI implementation (P1-09).

## Test plan

Validate `expected.init`, `expected.status_by_revision`, `expected.why_active_commitment`, `expected.admission_replies` and `expected.replay_as_of` from `wire-v1.json`. Validate an error envelope for each failure code in `kernel-v1.md`. Validate the design's tool contract example.

## Acceptance criteria

- AC-1 Every expected CLI reply in `wire-v1.json` validates against its schema.
- AC-2 An error envelope validates for each failure code listed in `kernel-v1.md`.
- AC-3 The design's tool contract example validates, and a tool contract without `effects` fails.
- AC-4 `exit-codes.yaml` lists exactly the codes in `kernel-v1.md`.

## Definition of done

Standard Definition of done.

## Escalate if

`kernel-v1.md` and `wire-v1.json` disagree about a reply shape.
