# P3-06 Stub and test-skeleton generators

## Goal

Go and TypeScript stubs, doc comments, interface files and table-driven test skeletons generated from function and module contracts, marked as generated.

## Context

Design: Data contracts (generated from each kind) and Tools. This also replaces the hand-written `zz_stub.go` files of the P0 to P2 workflow.

## Design

- `text/template` templates per language and contract kind under `templates/`.
- Function contract to a stub whose body panics with `unimplemented: <contract>`, a doc comment with pre- and postconditions, and a test skeleton with one row per example.
- Module contract to a package skeleton with the interface file and a depguard or dependency-cruiser rule fragment.
- Every generated file starts with the standard `Code generated by purser; DO NOT EDIT.` header and the contract digest.
- Output is formatted with `gofmt` or `prettier` and is byte-stable.

## Out of scope

Running the compiled skeleton (P3-07).

## Test plan

Golden outputs for the design's example contract and for each P1 kernel contract; a contract change that must change the digest line.

## Acceptance criteria

- AC-1 The design's `billing.ApplyCredit` contract generates the Go stub, doc comment and test skeleton in its golden files.
- AC-2 A TypeScript function contract generates the stub and vitest skeleton in its golden files.
- AC-3 Generated Go files compile and the generated tests fail with `unimplemented`.
- AC-4 Generation is byte-stable across runs.
- AC-5 Every generated file carries the generated header and the contract digest.

## Definition of done

Standard Definition of done.

## Escalate if

A contract kind cannot be mapped to a stub without inventing behaviour.
