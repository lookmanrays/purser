# P0-04 Contract schema v1

## Goal

The contract file format becomes a JSON Schema with a loader and validator, and every drafted contract in this batch validates against it.

## Context

Contracts are how design decisions reach the builders. See the design's Data contracts section and `contract-v1.draft.md`.

## Design

- `contracts/format/contract-v1.schema.json` encodes the draft's keys, the requirements per kind, and the rules: function contracts need an example or a vector reference; error codes are snake case.
- `internal/contract.Load(path) (Contract, error)` parses YAML into a typed struct and validates it. `Digest(path)` returns the SHA-256 of the file's exact bytes.
- `tools/contractcheck` validates one file or every file under `contracts/`; `make check` runs it.
- `allowed_imports` in module contracts is cross-checked against `.golangci.yml`, and any mismatch is reported.

## Out of scope

No code generation from contracts (P3-06) and no kernel registration of contracts (P3-03).

## Test plan

The design's `billing.ApplyCredit` example and every file under `contracts/kernel/` and `contracts/graph/` must pass. Write negatives: unknown kind, missing `owner`, a function without examples or vectors, a camelCase error code, and a module without a layer.

## Acceptance criteria

- AC-1 Every contract file in this batch validates.
- AC-2 The design's example contract validates.
- AC-3 Each negative fixture fails with a message naming the key.
- AC-4 `Digest` is stable across runs and changes when one byte changes.
- AC-5 `contractcheck` exits 1 when a module contract's `allowed_imports` differs from the depguard rules.

## Definition of done

Standard Definition of done. You approve the format.

## Escalate if

A drafted kernel or graph contract needs a key the draft format lacks. Propose the key rather than bending the contract.
