# P2-01 Graph store and query API

## Goal

A derived, rebuildable SQLite index of modules, packages, files, symbols and tests with typed edges, a query API every later role uses instead of reading files, and a deterministic digest of its content.

## Context

The design's system graph: roles ask for a symbol's interface, its callers, its tests and its reuse candidates. The graph lives outside the kernel log, and only its digest is recorded (P2-08). Layer rule: `internal/graph/...` imports no kernel package.

## Design

- Separate database file, default `.purser/graph.db`, WAL mode. It can be deleted and rebuilt at any time.
- Node and edge shapes exactly as the contract's `data` section. Node IDs are stable strings with a type prefix: `mod:`, `pkg:`, `file:`, `sym:` (the SCIP symbol string), `test:`.
- Writes go through `Replace(batch, meta)`: in one transaction, delete every node owned by the batch's files plus edges from those nodes, then insert the batch. Edges into deleted nodes remain as dangling edges and are reported by `Stats`, so incremental updates (P2-05) can repair them.
- Reads: `Node`, `Find` (by name, kind, language, path prefix), `Edges` (in, out or both, filtered by kind), `Neighbors` (breadth-first to a depth, with a node limit), `Interface` (the exported signatures of a package), `Meta`, `Stats`.
- `Digest()` is SHA-256 over the canonical row stream: nodes sorted by ID, then edges sorted by (from, kind, to), each row marshalled from a fixed-field struct with `encoding/json` and ended with a newline. Metadata timestamps are excluded.
- Indexes on `nodes(name)`, `nodes(path)`, `edges(from, kind)` and `edges(to, kind)`.

## Out of scope

Indexing (P2-02, P2-03), incremental logic (P2-05) and recording the digest in the kernel (P2-08).

## Test plan

Hand-built batches for a small Go module and a small TypeScript package. Replace a file and check that its old nodes and outgoing edges are gone and that dangling edges are counted. Run queries at depth limits. Check digest stability under different insertion orders.

## Acceptance criteria

- AC-1 Every node and edge written can be read back field for field.
- AC-2 `Replace` for a file removes exactly that file's nodes and their outgoing edges and inserts the new ones atomically; a failure mid-batch leaves the previous state.
- AC-3 `Neighbors` respects depth, edge-kind filter and node limit, and never returns a node twice.
- AC-4 `Interface(pkg)` returns exported symbols with signatures, sorted by name.
- AC-5 `Digest` is identical for the same content written in different orders and changes when any node or edge field changes.
- AC-6 `Stats` reports node and edge counts by kind and the number of dangling edges.
- AC-7 A lookup by exact name on a store of 200,000 nodes returns in under 5 ms on CI hardware.
