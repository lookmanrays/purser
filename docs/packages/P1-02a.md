# P1-02a Store: schema and transactions

## Goal

A durable SQLite event log where one transaction numbers, hashes and projects a batch of events, plus the projection model and its reducer registry.

## Context

The store is the only write path under the gate. Spec: `kernel-v1.md`, Ownership and compatibility.

## Design

- SQLite through `modernc.org/sqlite`, with WAL mode, `synchronous=FULL` and `BEGIN IMMEDIATE` for write ownership.
- Tables: `events` (revision, canonical bytes), `receipts`, `records`, `edges`, and `meta` (head revision and head hash). Events are stored as their original canonical bytes.
- `Transact(actorID, proposalID, clock, decide)` takes write ownership, reads the current projection, samples the clock once and calls `decide(snapshot, at)`. It then numbers, hashes and applies the returned events and commits everything in one transaction. An error from `decide` rolls back. Empty events change nothing.
- `internal/kernel/projection` holds Record, Edge, Receipt, State and Projection, sorted as the spec says. A Registry maps (event type, version) to a pure reducer and rejects unknown pairs with `unsupported_version`. `projection.Base()` registers the M1 events (`ProposalReceipted`, `CommitmentCreated` v0 and v1, `CommitmentEdited`, `ApprovalRequested`, `ApprovalResolved`, `CommitmentActivated`).
- `CommitmentCreated` v0 is upcast after hash verification by renaming `text` to `statement`.
- In this package, `Snapshot` may fold the log from scratch for correctness. P1-02b replaces that with materialized reads.

## Out of scope

Admission rules and operators (P1-03). Fast reads (P1-02b). Replay and verification commands (P1-02c).

## Test plan

Drive `Transact` with `decide` callbacks that return the wire vector's event descriptions under its fixture clock. Compare event bytes, hashes and head after each batch. Inject faults between insert and commit. Test projection sorting and checksums against the vector checkpoints.

## Acceptance criteria

- AC-1 Replaying the wire vector's batches through `Transact` produces byte-identical events and the same head hash after each batch.
- AC-2 The snapshots at revisions 4 and 8 equal `snapshot_at_4` and `snapshot_at_8` exactly, and `Hash("projection", …)` at each revision listed in `status_by_revision` equals its `projection_hash`.
- AC-3 A failure injected after the event insert and before commit leaves the previous head, events and projection unchanged.
- AC-4 An error returned by `decide` rolls back with no partial rows.
- AC-5 Empty event lists change nothing, not even the head.
- AC-6 An unregistered event type or version fails with `unsupported_version`, and the projection stays as it was.
- AC-7 A fresh store has revision 0, an empty projection and a head of 64 zeroes.
- AC-8 Folding each golden log from `tests/test_gate.py` scenarios through `projection.Base()` reproduces every recorded snapshot.

## Escalate if
