# P0-07 Quality harness: coverage and fuzzing

## Goal

Coverage floors and fuzzing run automatically, so quality cannot quietly slip. Benchmark ratio checks are P0-07b, split from this package when the build needed about 700 lines against a 350-line budget.

## Context

The design puts quality and stability first, and purser-main's quadratic replay must never return.

Three facts shape the design:

- `go test -fuzz` accepts exactly one package and a pattern that matches exactly one fuzz target. `go test -fuzz . ./...` fails with "cannot use -fuzz flag with multiple packages".
- A GitHub-hosted job is stopped after six hours, so one hour per target cannot run sequentially in a single job.
- Since Go 1.22 a package without test files appears in the coverprofile at 0%. `cmd/purser` is such a package today.

## Design

- `.coverage.yaml` sets floors: 85% for `internal/kernel/**`, 70% for everything else. Per-package overrides may only raise a floor. Explicit exclusions, each with a non-empty reason, cover packages that cannot meet a floor for a structural reason. The only exclusion today is `cmd/purser`, a two-line `main`. Unknown keys and floors outside 0–100 are rejected.
- `tools/covercheck` reads a coverprofile and `.coverage.yaml` and fails when a package is below its floor, naming each such package.
  - It accepts `set`, `count` and `atomic` modes; a block counts as covered when its count is above zero.
  - A block repeated in the profile counts once and is covered if any copy is, as `go tool cover` merges it.
  - A malformed line, a missing or unknown mode header, or a profile with no blocks is an error.
  - `make check` writes the profile with `go test -race -coverprofile` and runs covercheck on it.
- `covercheck fuzz-targets` lists every fuzz target as JSON objects with `package` and `name`, taken from `go test -list '^Fuzz' ./...` in a given module directory.
  - `make fuzz` runs each listed target for 30 seconds, one `go test -run '^$' -fuzz '^<name>$'` per target, and fails if any run fails.
  - The nightly workflow lists the targets in one job and fuzzes them in a matrix job with one entry per target, for one hour each. The matrix job sets `fail-fast: false` and a `timeout-minutes` above 60 and at most 360.
  - Any crasher fails the run; nothing ignores a failure (`continue-on-error`, `|| true`, `set +e`). On failure the workflow uploads the target's `testdata/fuzz` directory so the crasher can be reproduced.

## Out of scope

No fuzz targets or benchmarks of real packages; their packages add those.

## Test plan

- Coverprofile fixtures above, at and below the floors.
- Fixtures for repeated blocks, `atomic` mode with counts above 1, a malformed profile and an empty profile.
- Configuration fixtures: an override lowering a floor, an unknown key, and an exclusion.
- A fixture module under `testdata` (its own `go.mod`, no dependencies) with at least two packages, two fuzz targets in one package, and a non-target helper such as `func Fuzzy()`. Derive the expected `fuzz-targets` output by running `go test -list '^Fuzz' ./...` in it; never type it from memory.
- Assertions on the checked-in `.coverage.yaml` (loads; floors 85 and 70; every exclusion has a reason).
- Assertions on the checked-in `.github/workflows/nightly.yml`, parsed as YAML: schedule trigger, list job, per-target matrix, the timeout and `fail-fast` rules above, `-fuzztime 1h`, no ignored failure, crasher upload on failure.

## Acceptance criteria

- AC-1 `covercheck` fails when any package is below its floor and names the package; an excluded package is never reported.
- AC-2 A floor override below the default is rejected.
- AC-3 The nightly workflow runs every fuzz target listed by `covercheck fuzz-targets` for one hour each, one matrix job per target, and fails on any crasher.

## Definition of done

Standard Definition of done. `make check` passes on `main` with covercheck enabled.

## Escalate if

A floor cannot be met for a structural reason other than those listed, such as generated code; propose an explicit exclusion instead of lowering it.
