# P3-04 Module-lead session

## Goal

The module-lead role: refine one module contract into function contracts, unit test specs and leaf work nodes, as a plan bundle scoped to that module.

## Context

Design: Roles and model tiers (Module lead) and the leaf budget in the definition of done.

## Design

- Input: the module work item, its accepted contract, the module's graph slice and reuse candidates.
- Output: a module-scoped bundle with function contracts (each with examples), leaf work nodes (one function or a small cohesive set, within the leaf budget), unit test obligations and dependencies.
- Conformance: every exported function the module contract lists is produced by exactly one leaf; no leaf writes outside the module's scope.
- A boundary the lead cannot meet becomes a contradiction to the architect (P4-10 implements the record; here the session returns `contradiction` with its reason).
- Prompt pack under `prompts/lead/`; CI uses replay mode.

## Out of scope

Implementation of leaves.

## Test plan

Golden module tasks with recorded responses; a module whose contract is unsatisfiable; leaves over budget.

## Acceptance criteria

- AC-1 Each golden module task yields a bundle equal to its golden file.
- AC-2 Every function in the module contract maps to exactly one leaf.
- AC-3 A leaf over the leaf budget is split or the bundle is rejected before proposal.
- AC-4 An unsatisfiable module contract yields a contradiction result, not a bundle.

## Definition of done

Standard Definition of done.

## Escalate if

Leaf budget defaults are not set yet (they come from the first leaf bench).
