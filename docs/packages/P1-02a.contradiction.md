# P1-02a frozen wire tests receive the wrong numeric type

The SQLite dependency scope issue was resolved in #20. This is a separate blocker in the frozen acceptance inputs.

## Conflict

[`testvectors.Wire()`](../../internal/testvectors/loader.go#L188) uses `json.Unmarshal` to populate `map[string]any` fields. This converts JSON numbers in the event and snapshot maps to `float64`. The frozen [`playBatch` helper](../../internal/kernel/store/store_test.go#L73) asserts that each event's `event_version` is `int64` while constructing its arguments, before it calls `Transact`. The frozen [byte comparison](../../internal/kernel/store/transact_test.go#L49) also feeds those event maps to `codec.Encode`, whose [contract](../../contracts/kernel/codec.yaml#L87) excludes floating-point values.

## Evidence

A standalone Go probe against `origin/main` at `6ac52cc` and the frozen test baseline `f62ba0c` called `testvectors.Wire()`, encoded the first event and repeated the frozen assertion:

```text
event_version=1 (float64)
codec.Encode(w.Events[0]): invalid_value
snapshot_at_4.records[0].changed=1 (float64)
panic: interface conversion: interface {} is float64, not int64
```

AC-1, the store portion of AC-2, AC-3, AC-5 and AC-6 all reach `playBatch`. The first batch cannot reach the SQLite implementation. The projection portion of AC-2 also receives snapshot numbers as floats.

## Proposed resolution

Fix `Wire()` in the shared fixture loader on `main` so nested JSON integers reach callers as `int64`. Decode with `UseNumber` and normalize the dynamic fields recursively, following the loader's existing `Golden()` path. Add regression coverage for the wire event and expected projection maps. Rebase `build/P1-02a` onto that fix and rerun the acceptance checks with the frozen tests byte-identical to the existing tag.
