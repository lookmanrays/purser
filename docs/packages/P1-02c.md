# P1-02c Store: replay and verification

## Goal

`Replay` rebuilds projections from verified history and installs them atomically; `Verify` checks the whole log without writing.

## Context

Continuity without models relies on this. Spec: `kernel-v1.md`, the store row and the legacy fixture paragraph.

## Design

- `Verify` checks stored bytes, the contiguous chain, batch boundaries and known versions before interpreting anything, and returns the first bad revision.
- `Replay` verifies, folds into fresh tables and swaps them in under the write reservation. Readers see either the complete old state or the complete new state. On failure it rolls back and reports the first bad revision.
- An optional trusted head (revision and hash) detects a missing suffix.

## Out of scope

The CLI command (P1-09).

## Test plan

Replay the legacy vector; flip one byte at revision N; delete the last batch and replay with a trusted head; run concurrent readers during replay.

## Acceptance criteria

- AC-1 Replaying the legacy vector gives `expected_projection_hash` and `expected_head_hash`.
- AC-2 One flipped byte at revision N fails with `integrity_error` naming N, and the installed projection is unchanged.
- AC-3 With a trusted head, a missing final batch is detected.
- AC-4 Concurrent readers during replay always see a complete old or new snapshot.
- AC-5 Replay at the head returns the same snapshot as `Snapshot(nil)`.

Standard Definition of done.

## Escalate if

Atomic swap cannot be achieved inside one SQLite transaction.
