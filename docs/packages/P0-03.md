# P0-03 Record schemas

## Goal

JSON Schemas for every wire shape and record kind, plus Go types and a validator, so all later packages share one definition of the data.

## Context

The kernel's records, events, proposals and receipts are frozen by purser-main's vectors. The design adds v2 kinds. See `records.draft.yaml` and VOCABULARY.md.

## Design

- JSON Schema draft 2020-12 files in `contracts/records/`: `proposal`, `binding`, `event`, `receipt`, `snapshot`, `record` (envelope), one `fields.<Kind>.schema.json` per v1 and v2 kind (PascalCase, as the reference writes kinds), plus `WorkSpec.schema.json`, and `answers.schema.json` for q01 to q10.
- Every object schema sets `additionalProperties: false`; field sets are closed per version.
- v1 field sets are derived from the vectors and golden logs, not invented. When the draft and the recorded data disagree, follow the recorded data and note it in the PR.
- v2 kinds follow `records.draft.yaml` exactly.
- Graph schemas `graph.node`, `graph.edge` and `graph.meta` from the `data` section of `contracts/graph/store.yaml`, so P2 can start in parallel with P1.
- `internal/schema` exposes `Validate(schemaName string, value any) error` with a typed error carrying the JSON pointer of the first violation, and hand-written Go structs for the envelope shapes.
- Schemas are embedded with `go:embed`, so validation needs no files at run time.

## Out of scope

No kernel logic and no canonical encoding (that is P1-01). No Go structs for per-kind fields: the kernel keeps `fields` as validated maps.

## Test plan

Validate every proposal, event, receipt and snapshot in `wire-v1.json`, and every record and event in the golden logs from P0-06. Add one positive and at least two negative examples per v2 kind: a missing required field and an extra field. Include an ID that breaks the grammar and a generated approval ID that matches it.

## Acceptance criteria

- AC-1 Every proposal, event, receipt and snapshot in `wire-v1.json`, and every golden-log event, validates against its schema.
- AC-2 Every record in `snapshot_at_4`, `snapshot_at_8` and every golden-log snapshot validates against the envelope and its `fields.<Kind>` schema.
- AC-3 Each v2 kind accepts its positive example and rejects its negative examples.
- AC-4 Any unknown field is rejected, at any depth.
- AC-5 IDs outside the grammar are rejected; `a:` followed by 64 lowercase hex is accepted only where generated approval IDs are allowed.
- AC-6 Validation errors carry the JSON pointer of the violation.
- AC-7 The graph node, edge and meta examples in `contracts/graph/store.yaml` validate, and a node with an unknown kind is rejected.

## Definition of done

Standard Definition of done. You approve the schemas before P1 builds on them.

## Escalate if

A record in the vectors cannot be described without loosening `additionalProperties`, or two vectors disagree about a field.
