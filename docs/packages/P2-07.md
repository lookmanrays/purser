# P2-07 Reuse finder

## Goal

Given a function contract or a symbol, rank existing symbols that already do the same job, with scores and reasons, so planners and observers can stop duplicate code.

## Context

The design's "reuse before write" rule: context packs list reuse targets (P3-02), and the reuse observer flags duplicates (P4-03b).

## Design

Score each candidate symbol as a weighted sum, with weights in the contract:

- Name: identifiers split on case and underscores, normalized, compared by token overlap.
- Signature: parameter and result types normalized (package qualifiers removed, aliases resolved where the graph knows them) and compared as multisets, with order as a tie-breaker.
- Text: BM25 over names, signatures and doc comments, using SQLite FTS5 when the driver provides it and an in-Go BM25 otherwise.
- Structure: same package or a package the target already imports gets a small bonus; test files and generated files are excluded.

`Find(query, limit)` returns candidates above a threshold, each with its total, the component scores and a one-line reason. Embeddings (sqlite-vec) are left for later; the query interface leaves room for an extra component.

## Out of scope

Model-based similarity.

## Test plan

A fixture repository with seeded duplicates: renamed copies, reordered parameters, a wrapper with a different name, and look-alikes that must not match (same name, different types). Queries come from small function contracts.

## Acceptance criteria

- AC-1 For every seeded duplicate, the original appears in the top three results.
- AC-2 Across the fixture queries, at most one result in ten above the threshold is a seeded look-alike.
- AC-3 Each result carries its component scores and a reason that names the strongest component.
- AC-4 Test files and generated files never appear.
- AC-5 Results are deterministic, with ties broken by symbol ID.

## Definition of done

Standard Definition of done.

## Escalate if

The thresholds needed for AC-1 and AC-2 conflict on the fixture.
