# Kernel contract v1

M0-A for architecture v0.5. [Wire vectors](wire-v1.json) give exact values for a new repository. [Worked trace](lifecycle-v1.json) gives semantic inputs and independently observable expectations through M4. The vectors are specifications for future implementations. Dates, actor IDs and Git object IDs in the fixtures are synthetic.

## Ownership and compatibility

| Package | Interface consumed by the next worker |
| --- | --- |
| M1-A, storage | `purser.kernel.store.Store(path)`. Construction has no side effects. `initialize()` initializes an empty SQLite file or returns the verified existing snapshot. `snapshot(*, revision=None)` reads one completed batch, including from history. `replay()` verifies and folds the log into fresh projections and atomically installs them, returning the same head snapshot. All three return the snapshot defined below. |
| M1-A, gate-facing transaction | `store.transact(actor_id, proposal_id, clock, decide)` acquires SQLite write ownership, obtains the current verified projection and UTC time, and calls `decide(snapshot, at)` with the canonical UTC timestamp string. The callback returns an ordered list of `{"type":T,"data":P}` event descriptions and an opaque reply value, together as a pair. Empty events leave the log alone. The store numbers, hashes and projects the whole batch and returns `(committed_snapshot, reply_value)` after commit. An exception rolls back. Production write access is inside the trusted gate. |
| M1-A, shared semantics | A single pure event reducer owns projection changes. The gate reuses that reducer for evaluating a tentative multi-op batch. A registry of supported event type/version pairs rejects unknown history. M1-A and M1-C agree the concrete internal module layout. |
| M1-C, gate | `purser.kernel.gate.admit(store, binding, proposal, *, clock=...)` returns the durable receipt as a JSON object, or a typed error for a failure without a new receipt. `binding` originates in trusted ingress and contains `actor_id`, `role`, `principal_id`, `commitment` and `assignment`. The last two may be null for the owner. `clock()` yields a timezone-aware UTC instant. The public CLI supplies the host clock. |
| M1-B, consumers | `python -m purser --db PATH …` and read-only query rendering. Use the public store and gate above. The CLI owns argument parsing and serialization. A checker can read the same event fixture independently and reproduce the hashes below. |

The snapshot is `{"revision":int,"head_hash":hex,"projection":{"records":[],"receipts":[],"edges":[]}}`. Sort records by ID, receipts by (actor_id, proposal_id), and edges by (kind, from_id, to_id). Record shape is `{"id","kind","commitment","changed","fields"}`. Here and below, a set of quoted names denotes the exact object keys, and the linked vectors supply values. `changed` is the last event revision to change that record. Every record has one commitment. Edge shape is `{"kind","from_id","to_id","changed"}`. Core IDs are unique workspace-wide. A receipt's identity is its actor/proposal pair. A projection checksum is `H("projection", snapshot.projection)`.

A fresh store has revision 0, an empty projection and 64 zeroes as its head. A revision argument names the last revision of a *complete* batch, or zero. A revision in the middle of a batch or beyond the head fails with `bad_revision`. Replay has the exclusive write reservation while installing rebuilt projections. Published readers get a complete previous or complete new state. Roll back the installation on failure and surface the first bad revision. Verify the original stored payload bytes and the contiguous chain, including batch boundaries, before interpreting versions. A trusted retained head/backup identifies an entire missing suffix. An unanchored consistent prefix cannot do that.

## Canonical bytes and hashes

Allowed JSON values are null, booleans, strings containing Unicode scalar values, integers from −(2^53−1) to +(2^53−1), arrays and objects with unique string keys. The raw decoder rejects duplicate keys, nonintegers, nonfinite numbers, invalid UTF-8 and lone surrogates. Object field sets are closed at each version. Text is preserved as supplied, with no Unicode normalization. Validate before hashing. `C(x)` is UTF-8 without BOM or terminal newline of compact JSON using keys sorted by Unicode scalar value. Preserve array order. Escape strings as Python's JSON encoder does. For this restricted domain its exact settings are `json.dumps(x, ensure_ascii=False, sort_keys=True, separators=(",", ":"), allow_nan=False)`. An integer zero encodes as `0`. Reference vectors include non-ASCII and escaped text. [Python JSON](https://docs.python.org/3/library/json.html)

`H(tag,x) = lowercase_hex(SHA256(ASCII("purser/" + tag + "/v1") || 0x00 || C(x)))`. Use distinct tags `proposal`, `event`, `projection`, `outcome` and `effect`. A retained artifact is conventional SHA-256 of its exact bytes, with algorithm and digest recorded. Git IDs carry the repository's actual object format when used as candidate identities. UTC wire times use exactly `YYYY-MM-DDTHH:MM:SS.ffffffZ` and valid Gregorian dates. Deadlines are exclusive. A time equal to expiry is already expired.

A proposal's required fields are `v` (1), `proposal_id`, `commitment`, `base_revision`, nonempty ordered `ops`, and `justification` (an ordered array of reference strings, possibly empty). User-supplied record and proposal IDs match `[A-Za-z][A-Za-z0-9_.-]{0,95}`. Generated approval IDs use the reserved form `a:<64 lowercase hex>`. An operation's subject is scoped to its envelope commitment. Unknown or ill-typed envelope fields fail before receipt. A structurally valid envelope whose operation is unknown, malformed or ineligible receives a rejected receipt. `request_digest = H("proposal", {"actor_id":binding.actor_id,"proposal":proposal})`.

Each stored event has `v` (1), `event_version` (1), `revision`, `batch_start`, `batch_size`, `actor_id`, `proposal_id`, `at`, `type`, `data`, `prev_hash` and `hash`. `hash = H("event",event_without_hash)`. All entries in one batch share time, request identity, size and first revision. Revisions increase by one. The first event cites the previous complete head. Every later event cites the preceding event’s hash. Store original canonical event bytes or an equivalent losslessly verifiable representation. Type-specific upcasters interpret verified originals on read.

## Admission and durable outcomes

Check binding and envelope, then look up (actor_id, proposal_id) under write ownership. Same digest returns the latest receipt for that request, even if its supplied base is now old. A changed digest for an existing pair returns `id_conflict` without replacing the receipt or appending an event. Check a new request's base against complete batches. The gate derives its read dependencies from trusted operators. It checks current lifecycle, scope and those dependencies in the transaction that appends the result. Compare the committed starting state with the base before applying a proposal’s own ordered operations to tentative state. A changed read dependency since the base rejects with `stale_base`. Unrelated changes and diagnostic receipts alone do not stale the proposal. [SQLite transactions](https://sqlite.org/lang_transaction.html)

Read dependencies include absence for reserved IDs, the actor/assignment binding and its generation, trusted criterion and verification run, eligible evidence/waivers, parent-child set and coverage, dependency support/decision state, applicable grant and effect/attempt exclusion. An insertion or deletion affecting a previously read set counts as a change. A parent’s current child set cannot be checked by comparing only the old children's row revisions. Implement collection/absence versions or compute the equivalent validated history. Recheck current time and authority even if the base matches. A rejected multi-op batch saves no tentative domain effects.

`ProposalReceipted.data` contains `actor_id, proposal_id, digest, disposition, code, details`. Its projected/returned receipt adds `revision`, the batch's *last* revision. `disposition` is admitted, pending or rejected. `details` is an object. Ordinary success uses `ok` / `{}`. A held request uses `needs_principal` with `{"approval_id":id}`. `stale_base` includes `{"conflicts":[{"key":id_or_collection_key,"changed":revision},…]}` sorted by key. Authenticated, well-formed first-time rejections become a one-event receipt batch. A retry after lost acknowledgment returns that same disposition/revision. Administrative finalization can advance a pending origin receipt in a later batch. All earlier states remain in the log.

### M1 operators and event meanings

| Operation fields beyond `op` | State and events before the batch’s final receipt |
| --- | --- |
| `commitment.create` with `id,root,statement` | Principal or bound intake actor. ID must equal envelope commitment. Require two distinct unused IDs and a nonempty statement. `CommitmentCreated` carries the three fields plus `principal` from the trusted workspace. It creates a proposed Commitment and reserves its root as an open WorkItem, generation 1, with no candidate or parent. Execution waits for activation. |
| `commitment.edit` with `id,statement` | Principal or scoped intake actor may edit this proposed commitment's statement. `CommitmentEdited` carries both fields. Both operations can batch, with all preconditions applied in order. |
| `commitment.request_acceptance` with `id,expires_at` | Sole operation in its proposal. Require a proposed commitment, authorized requester and future expiry. `ApprovalRequested` contains `id,requester,request,request_digest,read_versions,expires_at`. The held action is activation of the exact proposed commitment. Record the original proposal and the versions it relied upon. Create an Approval record in pending state followed by the origin's pending receipt. |
| `approval.answer` with `id,request_digest,decision` | Sole operation, authenticated principal only. Decision is `approve` or `deny`. Recheck identity, matching origin digest, pending state, commitment, current time and original read versions. `ApprovalResolved` carries `id,state`, where state is approved, denied, expired or stale. Only a current approval emits `CommitmentActivated` with `id`. Finalize the origin receipt and write a separate admitted receipt for this valid answer, in the same batch. Include `approval_id` and final `state` in the answer receipt details. |

The original receipt becomes admitted / `ok` on activation or rejected / `approval_denied`, `approval_expired` or `stale_base` on the matching resolution. Preserve the approval ID on successful and denied/expired origin resolution. For stale origin resolution include the required conflicts. The response reads its own approval record and authorization binding against its supplied base. Inside a valid response, compare the origin’s saved versions against live data. A bad response digest, unauthorized responder or already resolved approval leaves the origin intact. Its own valid-envelope request gets the corresponding rejected receipt. If a request address is correct and the subject changed, a human answer can record that expiration/staleness even though the domain action is refused. Scope and claimed base for the answer are still checked. M1 activation gives permission to *begin scoped work*. Completion of the root requires a separate acceptance of a concrete outcome at M2.

The example establishes exact fields for Commitment, WorkItem and Approval projections. A pending Approval’s fields are its `ApprovalRequested.data` excluding the ID, plus `state:"pending"`. Resolution updates its state and changed revision. Commitment and root IDs remain reserved for their lifetime. Additional M1 semantic rejection codes are `unknown_op`, `invalid_op`, `forbidden`, `invalid_transition`, `id_exists`, `not_found`, `bad_revision`, `digest_mismatch`, `already_decided` and `approval_expired`. Details default to `{}` unless defined above. Error-code selection follows identity/dedup → base validity → per-op syntax and authorization → read conflicts → lifecycle and time predicates. Authorization and conflict errors never disclose another commitment’s data to an unbound caller.

## CLI surface and no-model answers

Use `python -m purser --db PATH COMMAND`. `init` returns `{"v":1,"revision":N,"head_hash":hex}`. A repeated init verifies the existing store. Other commands fail on a missing store. `propose FILE` reads one UTF-8 JSON proposal (`-` for stdin) and prints `{"v":1,"receipt":receipt}`. `status [--revision N] [--as-of TIME]` prints `{"v":1,"revision":N,"head_hash":hex,"projection_hash":hex,"as_of":time,"answers":object}`. `why ID` has the same read options and returns `{"v":1,"revision":N,"as_of":time,"record":record,"reasons":[{"code":str,"refs":[id,…]},…]}`. `replay [--as-of TIME]` rebuilds the complete log and returns the same object as status at its reconstructed head. Neither query parameters nor an executor can override the admission clock. With no `--as-of`, sample current UTC once per query and report the sample.

Machine replies are one UTF-8 JSON object on stdout plus a newline. Map-key order does not matter on stdout. Domain outcomes, including pending and rejected, use the receipt envelope. Other failures use `{"v":1,"error":{"code":str,"details":object}}`. Exit 0 for successful reads/init or admitted proposals, 2 for invalid CLI/encoding/envelope, 3 for a pending receipt, 4 for rejected proposals, `id_conflict`, missing records or invalid read revision, 5 for ingress authentication failure, 6 for unavailable storage and 7 for integrity/unknown-version failures. Failure without a receipt uses `invalid_input`, `unauthenticated`, `unavailable`, `integrity_error`, `unsupported_version`, `not_found`, `bad_revision` or `id_conflict` as appropriate. A history failure gives the first bad revision in details when identifiable.

Bind the human CLI to the private local workspace's owning OS principal, named `principal:local` in its namespace. Initialize under the trusted user's local account. An adapter cannot choose identity through JSON, flags or a ContextPack. M2's trusted fixture launcher constructs a role/assignment-scoped executor binding, a separately invoked observer binding and a verifier binding from the frozen harness. It supplies immutable candidate/definition identities. The ordinary CLI has no actor-selection facility. M1–M5 assume trusted local OS processes. M6 extends the check to an enforced process/transport boundary.

Answers are arrays ordered by first listed ID then subsequent identifiers, with identifier sets sorted and times in UTC. Include implemented question keys only. A supported question with zero matches is `[]`. M1 supports q01. M2 adds q02, q07–q10. M3 adds q03–q04. M4 adds q05–q06. Queries may return additional explanation references through `why`; these row keys stay stable.

| Key | Row keys and meaning |
| --- | --- |
| q01 | `commitment,principal` for active commitments |
| q02 | `work,state,generation,candidate` for current work. Candidate is an immutable typed identity or null. |
| q03 | `decision,state,support` with effective/reconsidering state and assumption IDs |
| q04 | `assumption,affected` with locally invalidated dependent IDs |
| q05 | `grant,commitment,grantee,capability,resource,expires_at,state` including expired/revoked grants, time-evaluated at the requested instant |
| q06 | `effect,attempt,state` for unfinished dispatches requiring reconciliation |
| q07 | `obligation,work,version,state,evidence` with qualified evidence or waiver references |
| q08 | `work,reasons` with sorted typed reason/reference objects |
| q09 | `commitment,root,missing` with the requirements still needed to satisfy that root |
| q10 | `action,subject` for currently permitted next steps, sorted by that pair. Principal-only actions are identified by their action name. |

M1 reasons use `awaiting_activation` referencing the commitment or approval, and `active_commitment` referencing its root. M2–M4 add reasons for missing current evidence, dependency invalidation, unresolved effect and outstanding root acceptance. Distinct reasons sort by (code, ordered refs). A historical query returns state as recorded at its named batch boundary. A specified evaluation time may change derived expiry only. Neither query nor replay obtains new observations or dispatches work.

## Evidence, decisions and the external-effect cutoff

A candidate identity is `{"kind":"git.commit","algorithm":"sha1"|"sha256","digest":hex}` for a commit, or a typed artifact identity with its verified digest. Tie a closing verdict to commitment, work ID, generation, assignment/result producer, exact candidate, obligation ID/version, verifier-run ID, observation ID and verifier identity. Bind trusted test definition and environment digests to that run. Each verdict refers to the same tuple as its observation and active criterion. Executor, independent observer and verifier get their identities from the launcher. A verifier may also be the observer, subject to the frozen criterion. Neither role can be the result producer for the same tested work. A historical run can remain useful for explanation after a generation changes. Only the current run can satisfy current obligations. A fail, inconclusive result or conflict blocks closure until an explicitly opened fresh run succeeds, or the principal waives precisely this criterion version and subject.

A leaf needs an explicit positive obligation. A structural parent requires nonempty declared children, its own obligations, and `all`, `any`, or `k_of_n` with 1 ≤ k ≤ n. Take all witnesses for all, the first qualifying child ID for any, and the first k qualifying child IDs for k_of_n. Define a candidate outcome from work ID, generation, exact candidate (nullable for a structural parent), coverage rule and declared child IDs, the selected children's outcome digests, supported decision revisions, obligation versions with qualifying evidence/run or waiver IDs, and required reconciled effect/observation IDs. Sort each set by ID. `H("outcome",basis)` names this JSON basis. Root acceptance names that digest and the commitment. Its own acceptance and subsequent closure event are excluded from the basis, so either can be rechecked after restart. Changes to an included fact invalidate its prior acceptance. The gate re-evaluates eligibility when the Closure Evaluator proposes close. A released commitment cannot reactivate through a late event.

Only a matching admitted trigger reconsiders a Decision. Invalidating A1 atomically changes which support qualifies at that revision. Traverse only incoming `depends_on` edges at every depth, deduplicate visited IDs, and evaluate tree coverage separately. Read-version dependencies include the current relation set as well as the reached nodes. A close or new dispatch ordered after invalidation cannot use the prior basis. If close committed first, invalidation makes its prior closure historical.

The gate binds one logical effect ID to a declared work/operation slot in its commitment and to an immutable Git intent. The intent contains repository identity, commitment, work, generation, assignment, slot, effect ID, capability, canonical branch, old and intended commit IDs, purpose and grant. Its digest is `H("effect",intent)`. A different caller-supplied key cannot create a second live operation for the same slot. The broker excludes overlapping unresolved dispatches to the same target ref, including after reassignment or a replacement intent. Each authorized physical attempt has its own durable ID and receipt reference derived from this logical intent digest, e.g. `refs/purser/receipts/<effect-digest>`. Repeated delivery of the same logical intent returns its current disposition. A successful logical effect is consumed. No new attempt is authorized until prior absence is established.

After slow preparation, acquire the single broker and the gate's write reservation, validate current scope and expected local state, sample the trusted UTC clock at authorization, and commit dispatching before issuing external I/O. Revocation and dispatch authorization have one durable order. Expiry equality or a revocation already effective at the cutoff refuses dispatch. A later revocation records the in-flight attempt and prevents new ones. Crash recovery always treats a durable dispatch with no terminal outcome as unresolved. Admission replay never invokes Git.

Observe the protected per-intent receipt and repository only after the earlier writer is quiescent, including possible surviving child processes. A matching receipt and verified target can establish success after a later legitimate branch advance. Confirmed absence requires intact receipt retention, the still-valid expected ref, and positive knowledge that the earlier writer cannot act or have applied an unrecorded transition under the qualified failure model. If the original grant still covers the action, re-authorize before a new physical attempt. A missing receipt alone, branch tip alone, inconsistent pair or unknown writer leaves the effect pending. A changed intention or fresh grant requires a newly admitted binding after the former intent is settled. [Git reference transactions](https://git-scm.com/docs/git-update-ref)

### Qualified design envelope

The M1 data path fits the single-machine POSIX, local SQLite and stdlib Python 3.11+ profile. The reference host has a Python 3.11 interpreter, local SQLite and Git. M0 vectors exercise the format and design hypotheses offline. Product isolation, paid model access, real-agent integration, backup destinations and operating/field duration are qualified at their scheduled gates. The runtime human may answer approvals locally. Remote delivery is optional.

The frozen legacy wire fixture uses `CommitmentCreated` event_version 0 with `text` in place of `statement`. Its pure upcaster changes this key *after* original hash verification. Every other field and derived record is unchanged. Write version 1 going forward. Other unsupported event versions produce `unsupported_version` and preserve the existing projection.

The worked trace freezes the concrete outcome-basis keys `work,generation,candidate,coverage,children,witnesses,decisions,obligations,effects`. Each witness is `{"work":id,"outcome":digest}`, each decision is `{"id":id,"revision":n}`, each obligation is `{"id":id,"version":n,"run":id_or_null,"evidence":id_or_null,"waiver":id_or_null}`, and each required external effect is `{"effect":id,"observation":id}`. `coverage` is null for a leaf or `{"kind":"all"|"any"|"k_of_n","k":int_or_null}` for a parent. `children` is the full ordered set of declared IDs, `witnesses` its qualifying subset. The resultant digests in the trace cover separate automatic-parent and principal-accepted root outcomes.

At M2–M4 `why` and q08/q09 reason codes include `missing_evidence`, `invalidated_support`, `effect_unresolved`, `awaiting_acceptance` and `missing_coverage`. q10 distinguishes `assign`, `observe`, `verify`, `rework`, `reconsider`, `authorize_dispatch`, `reconcile`, `evaluate_close`, `principal_approve` and `principal_accept`. A recorded grant never forces dispatch. When an attempt is unresolved, q06 reports its recorded state, and q10 exposes `reconcile` for that effect. The experimental scorer independently measures the real branch transition and the automatic parent's close decision.

Run `python3 docs/contracts/check_vectors.py` on Python 3.11+ to check the frozen bytes, batch linkage, receipt/projection checkpoints and worked effect/outcome digests. This checker imports only the standard library. Boundary conformance still requires exercising the actual store, CLI and Git in their assigned gates.
